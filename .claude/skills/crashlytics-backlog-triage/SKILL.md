# Crashlytics 백로그 트리아지

## 목적

Crashlytics에 쌓인 크래시와 ANR 이슈를 읽고, 실제로 고칠 가치가 있는 것부터 순서를 세운다.
판단은 사람이 하고, 이 스킬은 근거를 모아 정리한다.

CLAUDE.md의 글쓰기 원칙을 따른다.

## 범위

- 입력: Crashlytics 콘솔에서 복사한 이슈 목록, 스택트레이스, CSV/JSON export, ANR 리포트
- 대조 코드: Android `/Users/kimgideok/gf-client-android-kotlin`, iOS `/Users/kimgideok/AndroidProjects/gf-client-ios-swift`
- 읽기 전용 분석. 사용자가 명시적으로 승인하기 전까지 코드를 수정하지 않는다.
- 이 스킬은 이슈를 닫거나 Crashlytics 상태를 바꾸지 않는다.

## 워크플로우

1. 대상 범위를 먼저 확정한다. 앱 버전, 기간, 플랫폼, 이미 닫힌 이슈 포함 여부.
2. 이슈별로 사실을 모은다. 크래시 수, 영향 사용자 수, 첫/마지막 발생 버전, OS/기기 편중, 스택 최상단 프레임.
3. 스택트레이스의 최상단 자사 코드 프레임을 찾아 실제 파일 경로와 심볼로 옮긴다. 라이브러리 내부 프레임만 있으면 호출 경로를 역추적한다.
4. 같은 원인으로 보이는 이슈를 묶는다. 묶은 근거(동일 프레임, 동일 예외 메시지 패턴)를 남긴다.
5. 회귀 여부를 판단한다. 특정 버전부터 급증했는지, 그 버전의 변경 범위와 겹치는지.
6. 아래 기준으로 우선순위를 매긴다.
7. 재현 경로와 다음 행동을 이슈마다 한 줄로 적는다.

## 우선순위 기준

순서대로 본다. 앞 기준이 같을 때만 다음 기준으로 넘어간다.

1. 사용자 데이터 손실, 결제/업로드 실패, 로그인 불가 등 복구 불가 영향
2. 영향 사용자 수 (crash-free users 하락폭)
3. 최신 버전에서 새로 생긴 회귀
4. 자사 코드에 원인이 있고 수정 경로가 분명한 것
5. 증가 추세

내리는 요인: 단종된 OS/기기에만 발생, 이미 수정 커밋이 머지되어 다음 릴리즈에 나가는 것, OEM 버그로 우회만 가능한 것.

## ANR 취급

ANR은 크래시와 같은 줄에 두지 않는다. 메인 스레드 스택의 블로킹 지점(락 대기, 디스크/네트워크 I/O, 네이티브 호출)을 먼저 지목하고, 대기 대상이 무엇인지 코드로 확인한다. 확인 못 하면 `확인 필요`로 남긴다.

## 출력 형식

```markdown
## 결론

## 우선순위 목록

| 순위 | 이슈 | 예외/프레임 | 영향(사용자/건수) | 최초 버전 | 원인 위치 | 다음 행동 |

## 묶은 이슈와 근거

## 회귀 후보

## 원인 불명 / 확인 필요

## 재현 및 검증 경로
```

## 보호막

- 크래시 수, 영향 사용자 수, 버전 같은 수치는 입력에 있는 값만 쓴다. 없으면 `확인 필요`.
- 스택트레이스에서 읽히지 않는 원인을 추측으로 단정하지 않는다. 가설은 가설로 표시한다.
- 사용자 식별자, 이메일, 기기 ID 같은 개인정보는 문서에 옮기지 않는다.
- 두 플랫폼에서 같은 증상이 보이면 양쪽 코드를 모두 확인한 뒤에 공통 원인이라고 쓴다.

## 검증

- `./gradlew ...`는 실행하지 않는다.
- `rg`, `git log`, `git diff --check`, 대상 파일 읽기 같은 읽기 전용 확인을 사용한다.
- 회귀 후보는 해당 버전 태그 사이의 `git log`로 변경 범위를 대조한다.
